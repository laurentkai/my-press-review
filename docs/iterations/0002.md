## Réalisation

Le workflow `.github/workflows/deploy.yml` vérifie les PR vers `Main` et les pushes sur `Main` (et permet aussi le déclenchement manuel sur `Main`). Vérification : `npm ci`, `npm run format:check`, `npm run check` (typecheck, 29 tests et build), puis `npm run db:migrate:local` sur la seule base locale. Sur `Main`, le build vérifié est transféré comme artefact au job de déploiement.

Le job de déploiement, avec permission GitHub `contents: read`, s’arrête avec une notice et un résumé sans publication si `CLOUDFLARE_API_TOKEN` (secret), `CLOUDFLARE_ACCOUNT_ID` et `CLOUDFLARE_D1_DATABASE_ID` (variables) ne sont pas tous configurés. L’export `.release` contient uniquement assets construits, bundle Worker, migrations, configuration avec placeholder et manifeste SHA/hashes ; l’allowlist refuse fichiers, chunks ou configuration inattendus. Les IDs réels sont validés puis injectés uniquement dans `.deployment`, ignoré par Git. Ces IDs ne sont pas des secrets et peuvent potentiellement apparaître dans les journaux publics.

Le workflow vérifie le SHA complet contre le `Main` distant avant migration et promotion, sérialise les exécutions `Main` sans interruption, dépose le résultat de Time Travel D1 avant migration comme artefact de récupération de sept jours, déploie `.deployment`, puis promeut exactement `.release` vers `Production` dans un job distinct `contents: write`. Les migrations doivent rester compatibles avec le Worker N-1 ; aucun rollback de bundle ne restaure la base et aucune restauration D1 n’est automatique.

## Configuration et limites restantes

L’autodéploiement après push à `Main` et la promotion vers `Production` sont autorisés. La connexion Cloudflare de l’utilisateur, les variables/secret GitHub et les permissions effectives du token restent à configurer et vérifier ; aucun push distant, migration distante, premier vrai déploiement ou test de permissions du token n’a eu lieu.

Un échec après une migration distante peut laisser la base migrée sans nouvelle version du Worker. Si le déploiement réussit mais que `Main` avance ou que la promotion échoue, l’exécution peut être rouge alors que le service est déjà publié et `Production` n’a pas été actualisée. Il faudra diagnostiquer puis relancer sur le `Main` courant, jamais rerun un ancien commit. Les artefacts de build/release expirent après un jour ; après expiration, relancer le workflow complet sur le `Main` courant.
